Store a student once per company + role across mails

The placement cell does not send one list, it sends a series: an initial
list, a new one, then another that folds the previous ones in.  Extraction
now checks the rows other mails already hold for the same company and the
same normalised role before writing, and keeps the row already in the
database instead of adding a second one for somebody already stored.

Identity is the enrollment roll.  A name is only used when the row carries
no roll, because two different students in one list legitimately share a
name (Yash Chaudhary 23103042 and 23102113 both sit in the same Infosys
list, and matching on name dropped one of them).

Ownership follows each mail's own received_at, ties broken by id, so the
outcome is a property of the corpus and not of the order this run happened
to process the mails in - otherwise reprocessing a single older mail would
hand the student back to it and the row count would oscillate between two
states.  A mail with no role cannot be compared and is kept as is.

Golden ground truth for the 8 Sep Infosys niche list moves 37 -> 30: those
7 students were already listed by the earlier HackWithInfy status mail
under the same Infosys role, so the earlier row is kept.  They are still
on the card - a repeat only ever added a second row for someone already
stored.

with fan_out 1.0000 over 420 mappings.
